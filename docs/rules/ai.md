# AI の作業規則

## 始めるとき

1. `CLAUDE.md` に書かれた順にルールを読み、最初の返答の 1 行目で「ルール v<VERSION> を読んだ。対象: …」と報告する。
2. `docs/status.md` で、進行中の施策と実行中の計算を確かめる。
3. 対象の施策が決まっていなければ、人間に確かめる。新しい施策なら提案から始める (`lifecycle.md`)。

## 作業の単位

- **1 チャット = 1 施策。** 別の施策の話が出たら、その場で新しい施策の提案として切り出す (提案書を書いて PR を作るところまで)。
- 施策の外の小さな変更 (ルールの誤字、スクリプトの不具合) は `kind: infra` の施策にする。ルールの中身を変えるときは `docs/rules/VERSION` を 1 つ上げる。

## 書く場所

| 何 | どこへ | いつ |
|---|---|---|
| 方針・設計の決定、施策の判定 | `.okf/decisions/NNNN-*.md` (Decision) | 決まったその場で |
| 結果の数字 | `experiments/Exxxx-*/results/` (`scripts/collect.py`) | 計算が終わったら |
| 結果の解釈と判定の案 | `.okf/experiments/Exxxx-*.md` (Experiment) | 結果を見たら |
| 進行中・実行中の状況 | `docs/status.md` | 状況が変わったら |
| 採用した仕組みの設計 | `.okf/architecture/` (Architecture) | 採用の判定のとき |
| 外部資料・論文のメモ | `.okf/references/` (Reference) | 読んだとき |

チャットで決めたことや分かったことを、チャットの中だけに残さない。次のチャットは、リポジトリしか読めない。

## 書き方

- 文書とコメントは日本語。OKF の書き方は `okf.md`。
- 確かめていないことには印を付ける: **[確認]** (コード・数字・記録で確かめた)、**[推定]** (読み取れるが確かめていない)、**[不明]**。
- 数式は `$$` を独立行に置いたディスプレイブロックで書き、すぐ下に torch 上の shape を batch 込みで書く (例: `(batch, <=block_size, n_embd)`)。
- 線形変換は (N, D_in) × (D_in, D_out) = (N, D_out) の向きで書く (`nn.Linear` の weight が (D_out, D_in) であることに対応)。
- 設計の文書には現在の形だけを書き、以前との差分や経緯は書かない。経緯は Experiment と Decision にある。

## してはいけないこと

- 施策の中で `bench/` や `docs/rules/` を変える。
- 過去の数字を、今の施策の基準線として流用する (基準線は同じコード・同じ段階で測り直す)。
- 判定前のコードを `src/` に入れる。
- push していないコードで計算を回す、回してもらう。
- main に直接 push する。
- 人間が確認していない内容に `verified` を付ける。

## 人間に頼むこと

- 施策の開始の承認 (提案書の PR に「承認」とコメントしてもらう)。
- 採用の判定 (PR を main にマージしてもらう)。
- GPU のあるマシンでの計算 (`running.md` の形で、貼り付ければ動くコマンドを渡す)。
