# 評価の手順

## 1. 評価一式 (suite) は版で管理する

評価は研究とともに変わる (データ、指標、閾値)。変わること自体は止めず、**1 つの比較の中では評価を変えない**ことだけを守る。

- 評価データ・指標・閾値をまとめて `bench/suites/vN/suite.toml` に書く (書式は `src/project_name/lab/suite.py`)。
- **一度使い始めた版 (suite.toml を commit した版) は変更しない。** 変えるときは次の版を作る。
  評価データのハッシュは `suite.toml` に書き、テストと `scripts/run.py` が照合する。hooks も編集を止める。
- Proposal に、どの版で測るか (`suite: v1`) を書く。数字は必ず版とセットで読む。
- run の `meta.json` には、評価一式の版とハッシュ (`suite.sha256`) が記録される。採用の根拠にする数字は、このハッシュが今の版と一致するものだけ。
- 新しい版には、できるだけ前の版の評価データも含める (系列が途切れないように)。
- 学習データと評価データが重ならないことを、評価一式を作るときに確かめ、その方法を Proposal に書く。

## 2. 評価の変更も施策にする

- 評価一式を変えるときは `kind: bench` の施策を立てる。手順はほかの施策と同じ。
- **モデルの変更と評価の変更を、1 つの施策に混ぜない。**
- 新しい版を採用するときは、同じ施策の中で、基準線と現在の最良モデルを新しい版で測り直す。それが終わるまで採用としない。

## 3. 評価の見せ方

- 外部の処理 (後処理、探索、アンサンブルなど) を足した評価は、足していない評価と並べて報告する。何がモデルの実力で、何が外部の処理の効果かを分けて読めるように。
- どのモード・指標を報告するかは、評価一式の版ごとに `suite.toml` か `.okf/architecture/` に書く。

## 4. サンプルごとの出力を残す

- 評価では、集計値だけでなくサンプルごとの出力を `per_sample.jsonl` に残す。成否を表す真偽値は `ok` という名前にする (集計が成功率の区間を出す)。
- 指標は、残した出力から計算できるように書く。**指標を足すときに、再学習も再推論も要らない**ようにする。
- 評価データを足したときは再推論が要るので、残すべき学習済みモデルは保管しておく (`running.md` 4 節)。

## 5. 予算の段階 (tier)

| 段階 | 目的 | 規模の目安 (プロジェクトごとに `.okf/architecture/` で具体化する) |
|---|---|---|
| smoke | 動くかどうか | 数分。承認の前でも回してよい |
| screen | 見込みがあるか | 短い学習、seed 1 個 |
| confirm | 採用してよいか | 本番の学習、seed 3 個以上 |

- **採用の判定には confirm が必要。** screen までの結果では採用しない (短い学習の結論は長い学習で覆りうる)。
- 不採用の判定は screen で出してよい。ただし差が誤差の範囲なら `parked` にする。
- 段階を足すとき (候補をふるう probe など) は `kind: infra` の施策にする。

## 6. 基準線と誤差

- **基準線は、同じ版・同じ段階・同じ種類のマシンで測り直す。** 過去の施策の数字を流用しない。
- 基準線と候補は同じ seed で比べる。
- 集計ではブートストラップの 95% 区間を必ず出す (`scripts/collect.py` が出す)。
- 区間が重なる差は「差なし」として扱う。seed を足すか、段階を上げて確かめる。
